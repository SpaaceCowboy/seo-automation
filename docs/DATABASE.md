# Database Model

## 1. Principles

- PostgreSQL is the durable system of record.
- Stable entities and dated observations are separate.
- Observations are append-oriented and carry source/run provenance.
- Approval, execution, and measurement are distinct events.
- JSONB is acceptable for provider payload fragments and flexible evidence, but searchable business fields remain typed columns.
- Use UTC `timestamptz`; retain the site's IANA timezone for reporting.
- Use UUIDs generated by the application or database consistently.
- Soft deletion/disablement is preferred for business records; immutable audit events are never updated away.

## 2. Initial entity model

### Tenancy and operations

| Entity         | Purpose                                                    | Key constraints                                                              |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `sites`        | Crawlable RocoBroker site/property configuration           | Unique canonical origin; timezone and status required                        |
| `site_hosts`   | Allowed hosts/subdomains and scope rules                   | Unique `(site_id, host)`                                                     |
| `actors`       | Human/service identity used in audit trails                | Unique external identity where applicable                                    |
| `jobs`         | Application-level job status and correlation above pg-boss | Unique idempotency key per job type/site; timestamps and safe failure fields |
| `audit_events` | Append-only security and workflow audit                    | Actor, action, subject, timestamp, correlation, metadata                     |

### Crawl and page history

| Entity                         | Purpose                                            | Key constraints                                                                                    |
| ------------------------------ | -------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `crawl_runs`                   | One configured crawl attempt                       | Site, trigger, config snapshot, status, started/finished timestamps                                |
| `pages`                        | Stable normalized URL identity                     | Unique `(site_id, normalized_url_hash)`; retains normalized URL                                    |
| `page_snapshots`               | Fetch/extraction state for a page in a run         | Unique `(crawl_run_id, page_id)`; status, final URL, timings, hashes, metadata, indexability facts |
| `redirect_hops`                | Ordered redirect chain observed for a snapshot     | Unique `(page_snapshot_id, hop_index)`                                                             |
| `heading_observations`         | Ordered H1/H2 observations                         | Snapshot, level, position, text/hash                                                               |
| `structured_data_observations` | Parsed schema types and validation metadata        | Snapshot, type, fingerprint                                                                        |
| `image_observations`           | Image source/alt presence required for checks      | Snapshot, normalized source, alt/hash                                                              |
| `link_edges`                   | Directed internal/external links observed in a run | Run, source page, target URL/page, relation, anchor/hash; deduplicate occurrence key               |
| `robots_observations`          | robots.txt fetch and parsed policy by run          | Run/site, status, content hash, fetch metadata                                                     |
| `sitemap_fetches`              | Sitemap document fetch history                     | Run, URL, status, hash, parent sitemap                                                             |
| `sitemap_entries`              | URL membership and optional lastmod                | Run, sitemap fetch, normalized URL/page                                                            |

`page_snapshots` should include typed columns for `http_status`, `fetch_status`, `content_type`, `response_ms`, `final_url`, `canonical_url`, `meta_robots`, `x_robots_tag`, `is_indexable`, `indexability_reason`, `title`, `meta_description`, `word_count`, `content_hash`, `html_hash`, `render_mode`, `fetched_at`, and parser version. Optional compressed raw HTML requires an explicit retention decision.

### Deterministic analysis

| Entity              | Purpose                                          | Key constraints                                                        |
| ------------------- | ------------------------------------------------ | ---------------------------------------------------------------------- |
| `issue_definitions` | Versioned catalog of deterministic checks        | Unique `(code, rule_version)`; severity and remediation metadata       |
| `issue_occurrences` | Evidence that an issue existed in a run/snapshot | Unique natural occurrence key; source observations are not overwritten |
| `analysis_runs`     | Versioned execution of a deterministic ruleset   | Site, source run/window, ruleset version, status                       |
| `page_metrics`      | Derived per-run graph/page facts                 | Run/page; crawl depth, incoming/outgoing counts, orphan flag           |

Issue lifecycle views derive `OPEN`, `RESOLVED`, and `REOPENED` intervals by stable fingerprint across analysis runs. If explicit lifecycle records are later needed for performance, they must remain rebuildable from occurrences.

### Google data

| Entity                      | Purpose                                                              | Key constraints                                                     |
| --------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `integration_accounts`      | Non-secret identity/config for GSC/GA4/PageSpeed connections         | Provider, property identifiers, status; never store tokens directly |
| `integration_sync_runs`     | Import window, cursor, status, counts, and errors                    | Provider/site/date range/dimensions, idempotency key                |
| `search_queries`            | Stable normalized query identity                                     | Unique normalized query/hash; preserve display form                 |
| `gsc_daily_metrics`         | Daily clicks, impressions, CTR, position by supported dimensions     | Unique site/date/page/query/country/device/search type/data state   |
| `ga4_daily_landing_metrics` | Daily organic landing-page sessions and engagement/conversion fields | Unique site/date/page/channel/dimension version                     |
| `pagespeed_runs`            | Point-in-time mobile/desktop API observation                         | Site/page/strategy/fetched_at/API version                           |
| `pagespeed_metrics`         | Typed lab/field metrics and category scores                          | Run/metric name/scope/percentile                                    |

GSC metrics retain whether data is final/fresh and the exact dimension set. Do not sum pre-aggregated rows across incompatible dimension sets. Store response metadata sufficient to explain omissions without indefinitely retaining secret-bearing raw payloads.

### Opportunities and agents

| Entity               | Purpose                                                     | Key constraints                                                                        |
| -------------------- | ----------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `opportunity_runs`   | Detection window and algorithm version                      | Site/type/window/config version/status                                                 |
| `opportunities`      | Stable opportunity record with evidence window              | Type, target page/query/topic, state, source run                                       |
| `opportunity_scores` | Versioned scoring components and total                      | Opportunity/scoring-config version; demand, impact, confidence, effort, business value |
| `scoring_configs`    | Named configurable weights, thresholds, and effective dates | Immutable published versions; weights validated                                        |
| `agent_runs`         | Supervisor/specialist invocation and provenance             | Agent, prompt/schema/model/provider versions, status, tokens, cost, latency            |
| `agent_evidence`     | References to source rows supplied to an agent              | Agent run, evidence type/id, optional minimized snapshot                               |
| `agent_outputs`      | Validated structured output or validation failure           | Agent run, schema version, JSONB payload, validation status                            |

### Recommendations, approval, ledger, and measurement

| Entity                    | Purpose                                                             | Key constraints                                                                   |
| ------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `recommendations`         | Stable recommendation identity and workflow state                   | Opportunity/target/type/risk/current version                                      |
| `recommendation_versions` | Immutable proposed change, rationale, evidence, before/after values | Recommendation/version unique; schema version and provenance                      |
| `approval_decisions`      | Append-only approve/reject/request-change/supersede events          | Recommendation version, actor, decision, reason, timestamp                        |
| `change_ledger_entries`   | Declared execution of an approved recommendation                    | Approved version, target, executor, executed_at, before/after, external reference |
| `change_events`           | Corrections, reverts, or subsequent execution events                | Ledger entry, event type, actor, timestamp, details                               |
| `measurement_plans`       | Baseline/window rules and due dates                                 | Ledger entry, metric definition version, 30/60/90 schedule                        |
| `measurement_results`     | Immutable observed result for a window                              | Plan/window unique per attempt/version; baseline/comparison metrics and outcome   |

Recommended enums:

- Recommendation risk: `LOW`, `MEDIUM`, `HIGH`, `SPECIAL_APPROVAL`
- Decision: `APPROVED`, `REJECTED`, `CHANGES_REQUESTED`, `SUPERSEDED`
- Result: `POSITIVE`, `NEUTRAL`, `NEGATIVE`, `INSUFFICIENT_DATA`, `REVERTED`
- Job/run status: `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED`, `PARTIAL`

## 3. Key relationships

```text
site -> crawl_run -> page_snapshot -> redirect/link/heading/schema/image observations
site -> page -> page_snapshots across time
crawl_run -> analysis_run -> issue_occurrences / page_metrics
site -> integration_sync_run -> GSC / GA4 / PageSpeed observations
opportunity_run -> opportunity -> opportunity_score
opportunity -> agent_run -> validated output -> recommendation -> versions
recommendation_version -> approval_decision -> change_ledger_entry
change_ledger_entry -> measurement_plan -> measurement_results
actor -> approvals / executions / audit_events
```

## 4. URL and query identity

URL normalization must be versioned and conservative. Store the original observed URL, normalized URL, and normalization version. Do not automatically discard query parameters until the site's allow/deny policy is approved. Redirect destination and canonical target are observations, not replacements for historical identity.

Queries retain original text while using a normalized form/hash for stable identity. Locale-aware normalization must not erase meaningful Persian/Arabic character distinctions without explicit tests.

## 5. Indexing and partitioning

Initial indexes support latest successful snapshot per page/site, snapshots/issues by run, open issues by severity/page, link traversal by run, GSC by site/date/page/query, due measurements, workflow queues, and audit lookup by subject/time.

Start without partitions until real volume is measured. Candidate high-volume tables are `page_snapshots`, `link_edges`, `gsc_daily_metrics`, and `audit_events`; introduce date/site partitioning only with evidence and a migration plan.

## 6. Retention and backups

- Business history, recommendations, approvals, ledger entries, and measurements are long-lived.
- Raw HTML and raw external payloads require a short, explicit retention period or should not be stored.
- Backups must be encrypted, tested through restore drills, and retained according to an approved VPS policy.
- Deleting a site is a controlled administrative process that respects audit needs and does not silently orphan records.

## 7. Migration rules

- Drizzle migrations are committed and reviewed.
- Additive changes precede backfills and constraint tightening.
- Destructive changes require a documented backup/rollback approach.
- Schema tests verify constraints, idempotency keys, and representative historical queries.

## 8. Phase 1 implemented schema

Migration `0000_hard_xavin.sql` creates only the foundation entities:

- `sites` and `site_hosts` for approved site identity/scope configuration
- `actors` for future attributable human/service actions
- `jobs` for application-level status and idempotency above pg-boss delivery
- `audit_events` for future append-oriented workflow/security audit records

Crawler, Google data, opportunity, agent, recommendation, approval, ledger, and measurement tables remain intentionally unimplemented until their approved phases.

The `jobs.idempotency_key` unique index is the application-level duplicate-delivery guard. pg-boss owns its separate `pgboss` schema and installation migrations.

### Commands

```powershell
pnpm db:generate  # generate a reviewed migration after editing schema.ts
pnpm db:migrate   # apply committed migrations to DATABASE_URL
```

The migration integration test applies the committed migration to `TEST_DATABASE_URL` and verifies the Phase 1 tables plus canonical-origin and job-idempotency uniqueness.

## 9. Phase 2 implemented schema

Migration `0001_loving_lady_bullseye.sql` adds:

- `crawl_runs` for immutable logical attempts, frozen safety configuration, status, and summary
- `pages` for stable site/normalized-URL identity
- `page_snapshots`, `redirect_hops`, `heading_observations`, `structured_data_observations`, and `image_observations` for dated extraction history
- `link_edges` for per-run internal/external observations
- `robots_observations`, `sitemap_fetches`, and `sitemap_entries` for discovery provenance
- `analysis_runs`, `issue_definitions`, and `issue_occurrences` for versioned deterministic findings
- `page_metrics` for per-run depth, incoming/outgoing counts, and orphan state

`page_snapshots` is unique by crawl run and stable page. Re-delivery of the same logical run updates that run's observation instead of duplicating it; a subsequent crawl creates a new `crawl_runs` row and new snapshots/link edges. Stable issue fingerprints across analysis runs support first/last detection and resolution/reopen derivation without mutating source occurrences.

Raw HTML is not stored. `html_hash`, normalized content fingerprints, typed fields, ordered observations, and safe structured fetch errors are retained instead.

### Phase 2 query baseline

A rolled-back PostgreSQL 17 fixture with 1,000 page identities and 10,000 internal-link edges completed the per-run incoming-link aggregation in 2.342 ms on the development machine. This confirms the initial run/target index is used; it is an engineering baseline, not a production latency SLA.

## 10. Phase 3 implemented schema

Migration `0002_phase3_google_data.sql` adds:

- `integration_accounts` for non-secret provider/property identity and an external credential reference
- `integration_sync_runs` for window, dimension set, status, request/row counts, unmatched counts, and safe failures
- `search_queries` for stable site-scoped normalized query identity
- `gsc_page_daily`, `gsc_query_daily`, and `gsc_page_query_daily` with independent natural uniqueness keys
- `ga4_page_daily` for the versioned organic landing-page dataset
- `pagespeed_snapshots` for timestamped mobile/desktop lab and optional field metrics
- `integration_unmatched_urls` (migration `0003_phase3_unmatched_urls.sql`) for exact invalid/out-of-scope provider URL diagnostics

Daily GSC and GA4 rows are upserted by provider-domain natural keys, so replaying a date window updates rather than doubles metrics. PageSpeed remains append-oriented by exact collection timestamp. Each mapped dataset stores the observed URL, normalized URL/hash, and normalization version; `page_id` is nullable so in-scope Google-only URLs remain observable without manufacturing crawler identity.

GSC dimension tables must be queried independently. Metrics from page-only, query-only, and page/query datasets can be filtered or reconciled but must not be summed as if they were disjoint observations.

## 11. Phase 4 implemented schema

Additive migration `0004_phase4_opportunities.sql` adds five tables and three enums:

- `scoring_configs`: site-scoped immutable configuration publications, exact content hash and descriptive version
- `opportunity_runs`: unique site/idempotency command, config/detector version, analysis window, frozen source snapshot, attempt count, status/errors/timings/statistics
- `opportunities`: unique site/fingerprint current projection, target IDs/URL, type/status, score and first/last detection timestamps
- `opportunity_scores`: one immutable scored candidate/evidence observation per run/opportunity with config provenance
- `opportunity_events`: append-only detector lifecycle transitions; operator transitions use existing attributable `audit_events`

Enums contain all six detector types, OPEN/ACKNOWLEDGED/RESOLVED/DISMISSED/STALE lifecycle states, and QUEUED/RUNNING/SUCCEEDED/FAILED run states. Indexes support site/status/score lists, type/page filters, historical observation lookup and analysis windows. Score checks enforce 0–100. Foreign keys retain run/config/page/query provenance. No existing Phase 1–3 schema or observations are changed.

Database triggers reject config/score/detector-event updates/deletions, run deletion, successful-run changes and changes to captured input/command fields. A new config or run is required to reinterpret source data. Input capture uses repeatable-read transactions; persistence and projection are atomic under a site advisory transaction lock. Replayed delivery returns the existing completed result. Daily source upserts never overwrite previously frozen inputs.

The current `opportunities` row is deliberately a projection; authoritative historical evidence and scores stay append-oriented. Query-group candidates use nullable page/URL targets rather than arbitrary competing pages. Complete histories remain queryable even though detail responses cap each history collection at 100 entries.

Forward recovery: disable Phase 4 consumers/routes and retain its tables/evidence while repairing. Do not drop tables or rewrite applied migrations. Frozen input snapshots increase storage; measure growth before proposing retention/partitioning changes under the existing ADRs.

## 12. Phase 5 implemented schema

Additive migration `0005_phase5_agents.sql` introduces:

- `agent_runs`: site/opportunity/source score/operator identity, frozen policy, prompt/schema versions, status/outcome, attempts, invocation count, booked integer cost and timestamps.
- `agent_evidence`: one immutable minimized/versioned/content-hashed evidence bundle per workflow, with exact source references.
- `agent_invocations`: unique run/agent/attempt identity, provider/model/version/input hash, UTC budget month, reserved/settled cost basis, token usage, HTTP status/request ID, safe error/retry classification and latency.
- `agent_outputs`: only schema/grounding-validated analysis, with a matching Supervisor DRAFT/non-executable attachment allowed once.
- `agent_budget_months`: rebuildable deployment-wide UTC-month reservation/spend projection and conservative active ceiling.

A workflow source selects the most recent analysis window, avoiding backfill insertion-order regression. Trigger serialization and unique site/idempotency keys prevent duplicate workflow identities. Calls are recorded before provider egress. Monthly budget locks plus row locks make reserve/settle accounting atomic; per-run session locks serialize workflows without holding transactions across external requests.

All costs/prices are integer nanodollars, using `BigInt` and integer-scale PostgreSQL `numeric`, returned as strings. Unknown/interrupted usage retains its reservation rather than becoming zero. Completed histories, evidence and call identities are guarded against mutation/deletion. Validated analysis cannot be replaced; a matching non-executable draft can be attached once. Operator triggers/retries append `audit_events`.

No `recommendations`, `recommendation_versions`, `approval_decisions`, Change Ledger or measurement tables are created. Those remain Phase 6. Disable consumers and retain evidence for forward recovery; do not rewrite shared migrations or drop history.

## 13. Phase 6 implemented schema

Additive migration `0006_phase6_workflow.sql` creates ten approved-domain/support tables:

- `recommendations`: stable source action/site/page/mode and current state/version projection.
- `recommendation_versions`: immutable numbered concrete proposal/rule/risk/confidence with source linkage through the recommendation.
- `recommendation_events`: immutable lifecycle/revision/implementation history.
- `approval_decisions`: immutable current-version human review and role-at-decision snapshots; approved versions are unique.
- `change_ledger_entries`: immutable approved-version manual implementation values/actor/time/reference/mode; unique version and site command key.
- `change_events`: immutable revert/metadata correction events; one revert per implementation.
- `change_baselines`: immutable numbered capture-time aggregates/provenance over the fixed pre-change window.
- `measurement_plans`: unique change/horizon definitions, durable maturity/due dates and scheduling projection.
- `measurement_runs`: unique plan/attempt key, actor/correlation and retry/status/timestamp metadata.
- `measurement_results`: immutable run/plan/baseline-version comparison/outcome/provenance/overlap records, one result per run.

Enums cover review state, SANDBOX/PRODUCTION, risk, operational measurement state and the five result states. Indexes support awaiting-review queues, page/time overlaps, baseline/version history and due-plan dispatch. Role/value/lifecycle validation remains in application contracts; cross-record database guards also block stale/unapproved ledger insertion, service approvals, old-version approvals and immutable history updates/deletions.

Baseline, plans and ledger commit together. Result creation, classified audit events and plan/run completion are transactional. Retrying a run returns its original result; a new attempt preserves another observation. Late baseline recapture never rewrites earlier results. Comparison uses PAGE metrics separately from query datasets and preserves optional/missing data explicitly.

Disabling consumers preserves all business history for forward recovery; no existing Phase 1–5 schema or shared migration is destructively changed. Metadata correction/revert records never overwrite ledger values or perform physical rollback.

## 14. Phase 7 read projections

Phase 7 adds no tables or migrations. `control-repository.ts` reads existing site/run/observation/workflow history through parameterized SQL and Drizzle. Lists use site filters, bounded limit/offset and stable tie-break sorting; expensive reads use READ ONLY transactions with five-second statement timeouts. Google datasets are aggregated independently with explicit dates and successful-source/final-data gates. Current opportunity components refer to `last_run_id`, preserving consistency when an older backfill is inserted later.

Issue comparisons use only successful crawls/analyses and expose first/last detection plus OBSERVED/NOT_OBSERVED without overwriting occurrences or inferring repair from an absent bounded page. Existing workflow detail/history limits remain in force. The database remains inaccessible to dashboard/browser code. Named session authority lives in the API's existing registry and active `actors`; the bounded single-process dashboard session store has no database identity/password table.

## Phase 7.5 operations

No new schema migration is introduced. Production uses PostgreSQL 17 with a dedicated non-superuser application login. The default domain statement timeout is 30 seconds; operational inspection uses a read-only transaction with a 5-second timeout. Encrypted custom-format dumps include domain history and queue state. Restore creates only a new isolated `roco_restore_*` database and never switches production connections. The daily job also creates a separate encrypted configuration/secrets archive, excluding the offline decryption identity. Recurring offsite durability requires administrator setup. See `OPERATIONS.md`.

## Integration status schema

Additive migration 0007 adds operational worker telemetry and indexed connection-check history. Worker boot identity fences stale credentials/configuration; completed check records cannot be updated/deleted. The existing shared UTC-month budget ledger remains authoritative. This telemetry does not create crawl/Google/agent evidence.
